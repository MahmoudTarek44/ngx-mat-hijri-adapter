Date adapter

Two adapters can drive a Material datepicker. Register one of them. HijriDateAdapter is the main adapter. NativeHijriDateAdapter is the alternative when the stored value has to be a JavaScript Date.

Main adapter

HijriDateAdapter

Stores a CalendarDate. Reactive fields, signal fields, and ng add use this adapter.

Alternative

NativeHijriDateAdapter

Stores a JavaScript Date at UTC noon. Use it for a datepicker whose form value has to be a Date.

HijriDateAdapter

This is the main adapter. It implements DateAdapter<CalendarDate> for the Umm al-Qura and Gregorian calendars. ng add registers it, and the reactive and signal fields provide their own instance of it.

provideHijriDateAdapter() registers the adapter together with MAT_DATE_FORMATS and MAT_DATE_LOCALE. Call it once from the application providers. Its options are:

  • calendar: 'gregorian' or 'islamic-umalqura'. Defaults to islamic-umalqura.
  • locale: digits, Gregorian month names, weekday names, and the first day of the week. Hijri month names stay the package's Arabic and English names. Defaults to ar-SA.
  • timeZone: used by today(). Defaults to the runtime time zone.
  • firstDayOfWeek: 0 for Sunday through 6 for Saturday. Defaults to the locale's week info.
  • formats: Material format slots. Defaults to HIJRI_DATE_FORMATS. Numeric dates render as day/month/year. Named dates render as day month, year.

A datepicker then stores a CalendarDate. Parsing accepts numeric dates, ISO YYYY-MM-DD in the adapter calendar, and Hijri month names, including Arabic-Indic and Persian digits.

NativeHijriDateAdapter

This is the alternative. It implements DateAdapter<Date> for the same two calendars. Use it when a datepicker's form value has to be a JavaScript Date. Reactive and signal fields keep using HijriDateAdapter.

provideNativeHijriDateAdapter() from ngx-mat-hijri-adapter/native registers that adapter with MAT_DATE_FORMATS and MAT_DATE_LOCALE. Register it instead of provideHijriDateAdapter(). Both providers supply DateAdapter, so the one registered for that injector is the one Material uses.

The options have the same names and defaults:

  • calendar: 'gregorian' or 'islamic-umalqura'. Defaults to islamic-umalqura. Intl receives gregory or islamic-umalqura.
  • locale: digits, month names, weekday names, and the first day of the week. Month names come from Intl for the active calendar, so an English short name such as Ramadan is Ram.. Defaults to ar-SA.
  • timeZone: the civil day today() reads. The stored value is still UTC noon of that day. Defaults to the runtime time zone.
  • firstDayOfWeek: 0 for Sunday through 6 for Saturday. Defaults to the locale's week info.
  • formats: the same Material slots, defaulting to HIJRI_DATE_FORMATS.

Intl formats and parses the day, with timeZone: 'UTC'. Month lengths and adding days, months, and years use an in-repo Umm al-Qura table for AH 1300–1599, the same range as the main adapter. Each stored Date is UTC noon, so a time zone cannot move the civil day. toIso8601() returns YYYY-MM-DD in the adapter calendar. deserialize accepts that string, or a Date, which it normalizes to UTC noon of that UTC day.

Both calendars run here. Each form value is a Date.

Locale is not the calendar

On both adapters, calendar and locale are independent. ar-SA does not select the Hijri calendar, en-US does not select Gregorian, and a Hijri calendar does not force Saturday as the week start. In this runtime, en-US and ar-SA start the week on Sunday, and ar-EG starts it on Saturday. setLocale updates those rules and leaves the calendar as it is.

Switching calendars

setCalendar() switches an adapter instance at runtime, and calendar reads the current one. Material redraws through localeChanges. On HijriDateAdapter, later reads convert the CalendarDate into the new calendar. On NativeHijriDateAdapter, the Date stays the same instant and later reads use the new calendar, so 1 Ramadan 1445 reads as 11 March 2024. Use setCalendar() on an adapter provided to a single component, as the form fields do.

Month indexing

Both adapters follow Material's 0-based months. The calendar helpers on the main entry are 1-based. createDate throws for a month outside 0–11, a day outside that month, or an Umm al-Qura year outside 1300–1599. Adding months clamps to the last valid day. Adding a year or month that leaves AH 1300–1599 returns an invalid date.

Time methods are not implemented.
